# 公务员晋升模拟器

Vue2 + Element UI 前端 / FastAPI 后端（只在考公时提供组卷与判档，不落库）/ 全部玩家数据存于浏览器 localStorage。

当前状态：**1.0.0，封盘发行版**。136 条本地事件、七种结局、4 套皮肤；
考公五题定起点单位，一局从 22 岁干到 60 岁。契约版本 `1.0.0`。

流程：`/` 报到登记 → `/exam` 五道录用考试题 → `/dashboard` 上任（即主界面）。
路由用 hash 模式，静态 `dist` 不需要部署层配任何回退规则。

## 怎么把它跑起来

**Windows**：双击根目录的 `start.bat`。装依赖、构建前端、起服务一条龙，
跑完打开 http://127.0.0.1:8000 就能玩。

**其他平台 / 手动**（三条命令）：

```bash
cd frontend && npm install && npm run build        # 构建前端产物
cd ../backend && pip install -r requirements.txt   # 后端依赖
python -m uvicorn main:app --host 0.0.0.0 --port 8000
```

**成品就是一个进程。** `backend/main.py` 末尾把 `frontend/dist` 挂到了根路径，
页面与 `/api/*` 同源同端口——不需要反代、不需要配跨域、不需要第二个服务。
挂载写在所有路由之后，否则 `mount("/")` 会把接口一起吞掉。

**API Key 不是必需的。** 本作不调用任何模型：事件由前端本地事件池抽取，
考公的组卷与判档都是读题库 + 算分。`.env` 里不填 Key 照样玩完整流程
（`/api/event` 那条路是留给补料脚本的，玩家路径不经过它）。

## 数据契约

### 前端 data()

`src/mixins/gameState.js` 的 `data()` 展开 `createInitialState()`，得到三个响应式根节点
（`player` / `resources` / `gameStatus`）外加一个仅存内存的 `loadResult`。

| 分组 | 字段 | 初始值 | 区间 |
|---|---|---|---|
| player | name / age / level / position / unit / salary / quarter / ap | 空 / 24 / 乡科级副职 / 副镇长 / XX镇人民政府 / 5800 / 第1年 Q3 / 3 | — |
| | unitType 单位类型 | 基层乡镇 | 核心部门 / 基层乡镇 / 边缘部门 / 常规局委 |
| | examScore 考公成绩 | 0 | 0–100，考完由 `applyExamResult` 写入，仅供界面显示 |
| resources | energy 精力 | 100 | 0–100 |
| | authority 威信 | 30 | 0–100 |
| | mgmt 向上管理 | 20 | 0–100 |
| | popularity 人缘 | 40 | 0–100 |
| | ability 工作能力 | 35 | 0–100 |
| | kpi 政绩 | 10 | 0–**150** |
| | risk 廉政风险 | 5 | 0–100（%） |
| | health 健康 | 100 | 0–100 |
| gameStatus | currentEvent / showEventModal / gameOver / gameOverReason | null / false / false / '' | — |
| | gameOverEnding 结局代号 | '' | peak / landed / purged / collapse |
| | eventCooldown 事件冷却 | {} | 对象，id → 冷却结束的**绝对季度序号**，入档，用于事件避重 |

> 注：`health` 按"第 8 项"追加在 `resources` 末尾。**存储键序是前后端共享契约的一部分，不因界面
> 布局而改动**——精力与健康在界面上相邻显示，是 `ResourceBar.vue` 里 `RENDER_ORDER` 在渲染层排序
> 的结果，`RESOURCE_LIMITS` / `RESOURCE_LABELS` / `createInitialState()` 三处的键序保持原样。
> 详见「界面展示顺序」一节。

### 存档结构

localStorage 键名 `gwy_promotion_save`：

```json
{
  "game_version": "1.0.0",
  "saved_at": "2026-09-19T12:00:00.000Z",
  "data": { "player": {}, "resources": {}, "gameStatus": {} }
}
```

**版本怎么比：只有主版本不同才清档**（`storage.js` 里的 `majorOf`）。
次版本之间互相读：`loadGame()` 把存档深合并到初始模板上补齐缺失字段、
收敛越界资源、修掉派生的单位与职务，所以"改了数值、加了事件"的老档照样能接着玩，
只是从读档那一刻起按新规则往下走。主版本不同则返回 `version_mismatch` 并**保留原存档**，
由界面弹窗提示后调用 `resetGame()` 重开——主版本变意味着契约不兼容，
硬读会把玩家带进一个规则错位的局里，那比让他重开更糟。

这条规矩是发行（1.0.0）之后才立的。开发期每动一次数值都清档，是因为那时清档免费
（世上只有测试档）；发出去之后它就有价了，代价是某个玩家正在跑的那一局。

落盘走白名单，不序列化整个 `$data`。

### 读档状态码

| 状态 | 含义 |
|---|---|
| `new` | 无存档，已按初始档案报到并立即落盘 |
| `loaded` | 读档成功（已与初始模板深合并、资源越界收敛、职务按新规则静默修正） |
| `version_mismatch` | **主版本**不同，契约不兼容，需提示重开 |
| `corrupted` | 存档无法解析 |

### 晋升条件字典

`promotionRequirements` 的语义：**键 = 当前职级，值 = 提任下一级的最低门槛**。
玩家当前「乡科级副职」需 `ability 40 / mgmt 30 / popularity 30 / kpi 0`，且 `riskMax 20`。

字典共 8 行，与职级阶梯 1:1。末行「省部级正职」是阶梯顶点，各字段为 0 作**终点占位**，
判定时由 `nextLevelOf()` 返回 `null` 直接拦截，不参与计算。

### 廉政风险一票否决

`riskMax` 是硬门槛，风险超标时不看其余四项是否达标，优先级最高。处置分三档：

| 条件 | 裁定 | 说辞 |
|---|---|---|
| `risk <= riskMax` | 通过 | 条件成熟，可提请研究提任 |
| `riskMax < risk <= riskMax + 15` | 暂缓提拔 | 此次提任暂缓 |
| `risk > riskMax + 15` | 纪委约谈 | 先到纪委谈谈话 |

分档余量由 `RISK_INTERVIEW_MARGIN = 15` 控制（建议值，待复核）。
裁定由 `evaluatePromotion(resources, level)` 纯函数完成，返回 `PROMOTION_VERDICT` 之一：
`promotable` / `pending` / `risk_suspended` / `risk_interview` / `terminal` / `no_config`。

### 玩法循环（一季多事、AP 驱动）

```
第1年 Q3   AP ●●●
  ├─ 推进工作 → 向后端要事件 → 选项 costAp:1 → AP ●●○ → 结算并自动存档
  │                                              └─ 立即结束判定（可能当场留置/倒下）
  ├─ 推进工作 → 向后端要事件 → 选项 costAp:2 → AP ○○○ → 结算并自动存档
  └─ AP 耗尽 → 进入下一季度
       ├─ ① 结束判定（在休整回血之前，避免"休整把人从留置线上捞回来"）
       ├─ ② 季度号推进、AP 回满
       ├─ ③ 休整：精力 +20 / 健康 +5（不含风险衰减）
       ├─ ④ 跨年（Q4→次年Q1）：年龄 +1，月薪按 3% 上浮并抹到整十位
       ├─ ⑤ 季末晋升裁定（按当季峰值风险，尚未衰减）→ 达标则提任（职级/职务/薪资 +15%）
       ├─ ⑥ 结束判定（登顶 / 到龄退休）
       └─ ⑦ 廉政风险自然衰减 -3 —— 放在最后，只影响下一季度
```

**顺序上的两处刻意安排**（都是防作弊/防误判，改动前请先看用例）：

1. **风险衰减放在裁定之后**。体制内没有"休息一个季度就能洗白超标风险"的说法，
   季末裁定应当按当季实际峰值判定。若先衰减，`riskMax=20` 时风险 36 会被减到 33，
   从"纪委约谈"（超 15）降格为"暂缓提拔"（超 20 以内），临界情况判定失真。
2. **结束判定放在休整之前**。否则玩家在事件里把风险顶到 100、把健康打到 0，
   点一下"进入下一季度"就会被 +5 健康 / −3 风险救回来，两个失败结局形同虚设。

事件结算后另有 `settleGameOver()` 即时判定，理由同上——当场顶到 100 就该当场结束。

### 七种结局

| 触发条件 | 代号 | 结局 | 基调 |
|---|---|---|---|
| 狡辩失败（判定书当庭宣读） | `corrupted` | 立案审查调查 | error |
| 风险触顶 100 | `purged` | 纪委监委留置 | error |
| 健康归零 | `collapse` | 倒在工作岗位上 | error |
| 登顶省部级正职 | `peak` | 光荣退休 | success |
| 年满 60 岁未登顶 | `landed` | 平安落地 | info |
| 风声里选了"走"，且走成了 | `rednotice` | 红色通缉令 | error |
| 风声里选了"走"，在登机口被拦下 | `caught` | 机场被拦 | error |

优先级按上表从上到下。`forcedEnding` 排在最前，因为它不是"状态到了某个阈值"，
而是**已经发生的事**——判决书宣读过之后，玩家手里还有多少风险值都不再相干。
其后是风险与健康两条"出事线"，再判登顶，最后才是到龄退休。
所以"60 岁且已登顶"判定为 `peak`（光荣退休），"风险 100 且已登顶"判定为 `purged`。

全部结局共用同一个结算界面（`components/GameOverModal.vue`），按结局代号换四套皮肤：
退休类红顶米黄、落马类灰暗黑底红字、通缉令深蓝白字、过劳白色黑细框。
界面是 `position:fixed` 全屏，不是第二个弹窗——结局已宣判，底下的工作台不该还能被点到。

数值分散在各自的权威文件里，不在 `engine.js` 里重复写一份：
职级阶梯与提任门槛在 `constants/promotion.js`，薪资与支出在 `constants/money.js`
与 `constants/gameConfig.js`，贪腐上限与申报红线在 `constants/assets.js`，
季度节奏在 `engine.js` 的 `TUNING`。

### 风声预警：跑路唯一的入口

`game/flee.js`。赃款 ≥ 300 万**且**廉政风险 ≥ 40 时，点「推进工作」会优先弹出
一次性事件「一个很久没打来的电话」——那通电话一辈子只响一次，
接过之后 `gameStatus.fleeWarned` 置位，这条线永久关闭（`onceFlag` 机制，与函询通知书同路）。

- **走**：成功率 `0.2 + min(0.6, 赃款超出 300 万的部分 / 100 万 × 0.2)`，
  即两成起、每多 100 万加 20 个点、封顶八成。铺路成本是**三成赃款**，
  成不成都不退，从家产里扣、同时冲减赃款账（两笔账必须同一个数）。
  成功→红色通缉令，失败→机场被拦。两条都是终局。
- **不走**：`gameStatus.fleeRefused` 置位。下个季度的季末结算**直接立案审查**
  （`engine.js` 的 7.5 步），这一季连财产申报都不再走——申报那一套
  （差额分档、养鱼期、约谈）成立的前提是"组织上还不知道你贪了多少"。
  立案决定书里照旧只有三条狡辩与一次认罪退赃，**没有跑路这一项**。

工作台上不再有「卷款跑路」按钮（本版撤掉）。原因见 `game/flee.js` 开头：
按钮一亮，玩家就会围着它攒钱、卡着风险线走，跑路从"走投无路时有人递来一张船票"
变成了通关流程里的一步。现在能决定的只有接完电话之后走不走。

> 更早那一版是"赃款 ≥ 500 万且风险 ≥ 60 → 解锁按钮"，实测跑路率 0%：
> 越得过 500 万的 28 局在越线当下风险只有 0~35，够不着 60 就先被立案了。
> 那一版连同这段分析留作历史，**新门槛（300 万 / 40）正是照着它定的**——
> 300 万是厅级立案线，风险 40 对应"已经有人在背后议论"。

### 界面展示顺序

`ResourceBar.vue` 用 `RENDER_ORDER = ['energy','health','ability','authority','mgmt','popularity','kpi','risk']`
对资源排序后渲染，精力与健康置顶，其余按"做人 → 做事 → 底线"排列。这是**纯渲染层**的排序，
存储与接口里的键序一律不动——视觉顺序去改存储结构，等于为了排版引入新的 Bug。

### 单位类型（`unitType`）

`player.unitType` 决定 AI 生成事件的**场景底色**。取值只有四个，前后端逐字对齐，
后端 `models.UNIT_TYPES` 与前端 `gameConfig.UNIT_TYPES` 不可各自增删：

| 取值 | 场景底色 | 典型事件 |
|---|---|---|
| 核心部门 | 两办/组织部/发改委，离权力近，事急事大 | 凌晨两点的材料 |
| 基层乡镇 | 乡镇街道，直面群众，矛盾贴身 | 堵在门口的乡亲 |
| 边缘部门 | 工青妇/史志办，清水衙门，无权无事 | 饮水机坏了 |
| 常规局委 | 业务局委，有窗口有执法，按部就班 | 大厅里的投诉 |

它同时作用于两条路径：

1. **AI 路径** —— `prompts.UNIT_TYPE_THEMES` 把该单位的日常描述注入用户提示词的
   「单位类型与场景底色」段；系统提示词另有第 6 条内容规则要求贴合单位类型。
2. **兜底路径** —— 四种单位各配一款静态兜底事件，AI 不可用时也不会退化成通用事件。

**校验从严**：与 `level` 一样用白名单，非法值（含 `'基层乡镇 '` 这种尾随空格）直接 422。
理由是单位类型直接决定题材，写错会让 AI 悄悄退化成通用事件而不报错——宁可当场炸。

**优先级**：兜底事件按 `廉政风险 > 健康 > 单位类型 > 通用` 选择。前两档是关乎玩法安全的
强制题材（风险触顶、健康归零都会直接结束本局），压过只影响代入感的单位类型——
一个风险 90 的乡镇干部，兜底给他「饮水机坏了」是荒诞的。

## 考公与分配单位

玩家在 `/` 填姓名报名，`/exam` 答五道题，交卷后由后端出具成绩单与录用通知，
点「去报到」把单位与初始加成写进 localStorage，跳 `/dashboard` 上任。

### 题型配比与分值（后端硬编码）

| 题型 | 题数 | 每题 | 小计 | 考什么 |
|---|---|---|---|---|
| 行测逻辑 | 2 | 20 | 40 | 披着体制内外衣的逻辑题（选村建广场、增长计算） |
| 职场情商 | 1 | 20 | 20 | 领导潜台词、黑话翻译、表态的分寸 |
| 基层突发对策 | 2 | 20 | 40 | 群众堵门、迎检整改、汛情处置 |

5 题 × 20 分 = 100 分，**全对即满分**。「伯乐加分」那一档已经撤掉：
它原本是补"10 道题的基础分 95 与满分 100 之间那道 5 分缺口"的；改成 5 题、每题 20 分之后，
基础分自己就是 100，缺口不存在了
（常量与响应字段还留着，值恒为 0，见 `models.EXAM_BONUS_MAX`）。

题量从 10 降到 5，是因为每次重开都要重做一遍卷子，10 道的负担压在开局上太重；
题库本身没动，仍是 50 道，只是每次抽 5 道。

### 分配红线（`models.EXAM_TIERS`，Python 写死）

| 总分 | 单位类型 | 去向 | 初始加成 |
|---|---|---|---|
| ≥ 80 | 核心部门 | 市委办公室 | 工作能力 +10、向上管理 +10、威信 +5 |
| 60–79 | 常规局委 | 市财政局 | 工作能力 +6、向上管理 +6、人缘 +6 |
| 40–59 | 基层乡镇 | XX镇人民政府 | 人缘 +10、工作能力 +5、政绩 +5 |
| < 40 | 边缘部门 | 市档案局 | 精力 +10、健康 +10、人缘 +5 |

对着"答对几题"看就是 4~5 题进核心、3 题进常规局委、2 题进基层乡镇、0~1 题进边缘部门。
半分那道算 10 分，**落在哪个档按分数走**，不为它单开规则
（所以"2 题满分 + 2 题半分 = 60 分"进的是常规局委，尽管答对的只有 2 题）。

### 题库判档，Python 算分

阅卷不是刚性对错，而是按「体制内智慧」弹性给分：

- 完美选项 → 满分；勉强合格 / 略显书生意气 → 半分；激化矛盾 / 推卸责任 → 零分

判档**查题库里写好的答案键**（`best` / `half` / `optionComments`），不调用模型：
作答只有四个选项可选，输入空间穷举得过来。分值与红线仍在 Python 手里：

```
earned = 每题分值 × {full: 1.0, half: 0.5, zero: 0.0}
score  = clamp(round(卷面分 + EXAM_BONUS_MAX), 0, 100)      # 后者恒为 0
```

于是分数不可能越界，也不可能把玩家分到表外的单位。题号与题型由 `EXAM_TYPE_BY_INDEX`
按序号覆写，**不采信题库自报的题型**；题库文件读不出来时整卷换成
`prompts.FALLBACK_EXAM_QUESTIONS`（5 道），并在 `meta.source` 标记 `emergency`。

### 防篡改：题型与权重按题号定，不听 AI 的

`_normalize_questions()` 对抽出来的卷子做硬校验：**必须正好 5 题、每题正好 4 个选项、
`best` 必须在选项内、题干非空**，否则整张卷子弃用、换内置兜底题库。

并且题号强制为 `q1..q5`、题型强制取 `EXAM_TYPE_BY_INDEX[idx]`——**不采信题目的自报题型**。
题型是绑定在**题号**上的（每题的题型决定它算进哪一行分项），
跟着题目自报的 type 走，成绩单上那三行（逻辑 40 / 情商 20 / 对策 40）就会与实际题型串位，
阅卷人评语里点名"拖后腿的那条线"也会指错。

### 交卷为什么要回传原题

后端不落库、服务端手里没有题库，所以 `/api/exam/evaluate` **必须随请求回传五道原题**。
代价是完美选项 `best` 会下发到前端（单人本地游戏、无对抗性，可接受），
换来的是阅卷完全可复现——不依赖任何服务端状态。（`best` 不进 localStorage，只活在内存里。）

### 弹窗与自动存档

- `showEventModal` **不入档**，读档时强制置 `false`。待办事件由 `hasPendingEvent()` 判定，
  界面据此亮红点，玩家主动点开——避免刷新页面导致弹窗重放、属性被重复扣减。
- 自动存档时机：**事件结算后 / 季度推进后 / 晋升裁定后**，各调用一次 `saveGame()`。

## 后端接口

后端只做 AI 中转，**不存任何玩家数据**：前端每次把完整 `PlayerStatus` 传上来，
服务端校验 → 拼提示词 → 调 DeepSeek → 校验返回 → 回传事件，请求结束即忘。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/health` | 健康检查，返回模型名、`api_key_loaded`、JSON 模式、超时 |
| POST | `/api/contract/validate` | 只校验报文合法性，**不调 AI**。联调先打通这个口 |
| POST | `/api/event` | 生成事件，永远返回可用事件（AI 故障自动兜底） |
| POST | `/api/exam/generate` | 出五道考公题，永远返回可用试卷（题库读不出来就换内置兜底） |
| POST | `/api/exam/evaluate` | 阅卷 + 算分 + 分档，永远返回成绩单 |

两个考公接口与 `/api/event` 同样是**不会因 AI 故障返回 5xx** 的。

### 请求

`POST /api/event` 的 body 就是前端 `buildPlayerStatus()` 的产物，与 `models.PlayerStatus` 一一对应：

```json
{
  "gameVersion": "1.0.0",
  "player": { "name","age","level","position","unit","unitType","salary","quarter","ap" },
  "resources": { "energy","authority","mgmt","popularity","ability","kpi","risk","health" },
  "gameStatus": { "currentEvent","showEventModal","gameOver","gameOverReason",
                  "gameOverEnding","eventCooldown" },
  "promotionRequirements": { "乡科级副职": { "ability","mgmt","popularity","kpi","riskMax" }, ... }
}
```

`models.py` 全部模型用 `extra="forbid"`，多一个字段就 422——宁可联调时炸，也不要静默吞掉字段名拼写错误。

### 响应

```json
{
  "event": { "id","title","description","options":[{"id","text","costAp","effects"}] },
  "meta":  { "source": "ai", "reason": "", "attempts": 1 }
}
```

外层包一层 `meta` 是为了让前端能分辨这次到底是 AI 生成还是兜底事件——调提示词时若没有这个信号，
很容易把兜底内容误当成 AI 输出。前端 `api/event.js` 会拆包，`views` 层拿到的仍是**裸 `GameEvent`**，
与 `mock/events.js` 的结构完全一致，业务代码不需要为"接 AI"做任何适配。

`meta.source`：`ai`（模型生成）/ `fallback`（后端兜底事件）。前端另有一档 `local`（后端整个不可达，
退回本地事件池），在 `api/event.js` 里生成。

### 降级链

```
后端 AI → 后端兜底事件 → 本地事件池 → null
```

任何一环出问题游戏都不会卡住。**本接口不会因为 AI 故障返回 5xx**：超时、非法 JSON、
格式跑偏一律降级为兜底事件并返回 200。

### 提示词约束（`prompts.py`）

分三层：输出格式（字段名、取值范围、纯 JSON）、内容（职级匹配 / 体制内话术 / **无完美选项** /
风险收益对称 / 措辞克制）、状态触发的强制题材。

**强制题材**由 `build_forced_theme()` 按状态注入，优先级高于模型自由发挥，两条可叠加：

- `risk > 50` → 必须是纪委暗访、函询谈话、巡视组下沉或同僚借题发难的人事斗争，不得出轻松日常
- `health < 30` → 必须围绕体检指标异常、住院、家属施压要求调岗

### 防御措施（`services/deepseek.py`）

1. **JSON 清洗** `clean_json_text()`：去零宽字符/BOM → 剥离 ```` ```json ```` 围栏 →
   取第一个 `{` 到最后一个 `}` → 去尾随逗号，然后才 `json.loads`
2. **归一化** `_normalize_event()`：`costAp` 收敛到 0–3；**若没有任何零消耗选项则强制造一个**，
   避免玩家 AP 耗尽时无路可走
3. **重试**：格式跑偏按 `DEEPSEEK_MAX_RETRIES` 重试（不含首次）
4. **兜底**：仍失败则 `pick_fallback(status)`，按 风险 > 50 → 健康 < 30 → 默认 三档挑贴合的一款
5. **`generate_event()` 从不抛异常**，返回值恒为 `(event, meta)`
6. **`_safe_error()`**：异常信息回传前端前抹掉 API Key

兜底事件同样遵守"无完美选项"，且在 `prompts.py` 导入时由 `_validate_fallbacks()` 断言校验
（字段结构、至少一个零消耗选项、effects 键合法）——写错在启动时就炸。

   先说清楚一件事，它推翻了本条目此前记的 45%：

   **45% 是在"完全没有避重"的口径上测出来的，不代表当前游戏的任何版本。**
   当时模拟器从不记录 `usedEventIds`，抽取链的每一档都不会被判成"抽干了"，
   玩家于是永远停在最窄的那一档。把 2.6.0 的冷却常数按 0 跑（等于复原那个口径），
